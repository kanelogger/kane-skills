# Git Rules

## 工作区与改动

- 开始前检查 `git status`，已有或并发修改视为用户资产，不覆盖、不混入本次改动。
- 每一行改动都应能追溯到当前需求；不打包无关修改。
- 报告变更清单或提交前，通读本次全部改动的完整 diff，而不是只看最后一次编辑；凡改动共享状态（store、缓存、数据库表、接口契约、全局配置），逐项列出其全部读取方与写入方，确认均已处理。
- 并行实现只是迁移手段：替换验证通过后必须删除旧路径，旧实现不得与新实现永久共存。

## 提交与推送

- 不擅自推送、发布、变基、改写历史或执行破坏性清理。
- 验证完成后报告变更清单和验证结果；不自动创建提交，是否提交、何时提交由用户决定。
- 用户明确要求提交后才执行提交；用户明确要求推送后才执行推送。提交授权不包含推送授权，普通实现或审阅任务不包含两者的授权。
- 本文件提供完整的仓库内流程，不依赖个人安装的 Git Skill。用户显式调用已安装技能时可以用它辅助执行，但仍遵守本文件的范围与授权约束。
- 用户要求提交时，一个逻辑变更形成一个提交；实现、测试和直接相关文档在同一个提交中。
- 只读任务不创建空提交；未通过的检查必须明确报告。

## 已授权提交的执行步骤

1. 核对当前仓库、分支、工作区和暂存区：读取 `git status --short --branch`、完整 `git diff` 与 `git diff --cached`，逐个查看本次候选未跟踪文件。区分本次改动、用户原有改动和其他任务改动。存在无关的已暂存内容，或同文件混合改动无法安全分离时，保留现场并澄清提交边界。
2. 审查候选内容及文件类型，排除真实密钥、凭据、个人运行状态和不应入库的生成产物。疑似敏感内容或归属不明时，暂停该提交，只报告路径、发现类型与风险，取得明确处理指示；不回显敏感取值。
3. 仅以显式路径 `git add -- <path...>` 暂存本次内容；同文件的独立改动按 hunk 暂存。不得用 `git add .`、`git add -A` 或宽泛通配符扩大范围，也不为准备自己的提交而撤销他人的暂存内容。
4. 重读完整暂存 diff、暂存文件版本及 `git diff --cached --check` 结果，确认与本次目标、敏感信息审查和已有验证证据一致。暂存区为空时不提交；复核后发生并发变化时重新核对。
5. 按仓库既有提交格式及用户要求撰写消息，说明实际改动、原因、已有验证结果与未验证项。多行消息写入临时文件，通过 `git commit -F <file>` 传入；不把用户文本或 diff 拼进 shell。保留 hooks，不擅自 amend、跳过检查或改写历史。
6. 提交后读取生成的提交及 `git status`，核对实际文件范围、提交哈希和剩余工作区改动。报告真实结果；只获提交授权时在此结束。

## 已授权推送的执行步骤

1. 核对当前分支、远端地址、上游和将推送的提交范围；远端目标不明确或包含范围不明的提交时先澄清。已有明确授权且目标可确定时直接继续，不重复请求同一授权。
2. 只推送已核对的分支到指定远端，不 force push、不推送全部分支或标签，也不自动发布。推送失败时保留本地提交并报告原因，不通过改写历史绕过失败。
3. 推送后读取远端目标分支的提交哈希，与本次推送的本地提交核对，再报告分支与结果。命令返回成功本身不代替远端回读。

## 分支命名

分支名要短，最多三个单词，用连字符分隔。不要使用斜杠，也不要使用 `feat/`、`fix/` 这类类型前缀。

示例：`session-recovery`、`fix-scroll-state`、`regenerate-sdk`。
