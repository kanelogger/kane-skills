## 事实源与索引

目标项目的 `.agents/context/index.json` 是给 Agent/LLM 使用的薄索引，随项目版本控制。它把语义 key 映射到现有文件、Markdown 段落或 YAML/JSON 字段；摘要只描述何时可能需要读取，不代替事实正文。

保留现有信息归属：

| 内容 | 所属来源 |
| --- | --- |
| 真实工具链、命令、服务和环境 | `project.yml` 及其引用的实际配置 |
| 业务规则、子系统职责、架构 | 现有业务、子系统或架构文档 |
| 有证据、可复用的项目经验 | 项目选定的经验库 |
| 当前任务目标、验收、决策、证据、进展和下一步 | 本次明确的任务文件或 Issue |
| 跨来源综合后确需独立保存的稳定结论 | 无既有归属时才用 `.agents/context/derived/` |
| 本机收据、技能生成的计划和本轮证据 | 被忽略的 `.agents/state/bootstrap/` |

不复制一份 `raw/` 原始资料，不建立全局 `active_task`，不把所有任务写成一份新的状态库。明确任务记录由当前请求或现有任务系统确定；不能由“最近修改的文件”自动推断。没有持久记录需要的小任务可在会话留证据，不为索引另建任务体系。上述资料由 Agent 在工作时维护，不要求人手工同步索引表。

只有“多个来源共同支持一个新结论、现有文件没有合适归属、后续任务确实会复用”同时成立时，才新增派生文档。派生内容应写明结论、适用范围、简短理由、来源和使结论失效的条件；索引的 `sources` 保存本次核实的文件摘要。单一已有段落直接引用即可。综合结论已有所属文档时，直接索引该段并登记源依赖，不迁移正文；例如 `project.yml` 的命令说明可依赖真实包配置或 CI 文件。

## 初始化时投放

初始化或修正接入时，Agent 完成以下工作；它们是接入产物，不是所有业务任务的通用验收门禁：

1. 找到已有 AGENTS、工作流、真实命令、业务说明和任务入口，保留内容归属与项目自己的开发方式，并确定经验库位置。
2. 建立或修正索引，让现有工作流与至少一条真实检查命令可按 key 读取，并为本次相关业务来源提供可用入口。key 名由项目语义决定。检查命令的静态校验规则见 `references/adaptation.md` 的“接入结构”。
3. 将本文件后面的读取和维护协议合并到目标 AGENTS，再把节点责任、独立评审和经验回写合并到项目实际工作流。已有独立工作流则从 AGENTS 直接链接，小项目可短内联在 AGENTS 中。
4. 把索引纳入版本控制，忽略 `.agents/state/` 等本机状态与各级目录中的 `.bootstrap-*.tmp`，检查上级忽略项没有误吞 `.agents/context/`。
5. 应用后运行 `verify TARGET --adoption`，处理入口、来源和过期项的报告。用真实 key 读取工作流、检查命令和本次相关业务来源，再核对工作流内的独立评审及回写规则。

可把索引 JSON、AGENTS 和工作流的最终正文纳入已有 `apply` 文件计划，一次审阅投放；也可在来源文档已存在后用 `context update` 建立索引。实际条目要建立当前文件摘要基线，便于后续检测变化：`context update` 会自动捕获；同批 `apply` 投放时按计划中的最终正文计算。任何写法都要保留现有未涉及条目，不用示例覆盖项目知识。

用户明确调用本技能后，由执行技能的 Agent 定位已安装的 `kane-agent-bootstrap/SKILL.md`，继而确定 `{baseDir}`；不要把当前机器的绝对路径写进项目 AGENTS。明确调用用于日常任务时只执行检索和维护，不重跑初始化访谈、环境准备或资产投放。

## 索引格式

```json
{
  "schema_version": 1,
  "entries": {
    "workflow": {
      "file": "AGENTS.md",
      "section": "开发工作流",
      "aliases": ["开发步骤"],
      "summary": "任务各节点的读取、验证和维护责任",
      "when": ["start", "plan", "handoff"]
    },
    "environment.test": {
      "file": "project.yml",
      "select": ["environment", "commands", "test"],
      "summary": "项目真实测试入口及前置条件",
      "when": ["start", "verify"]
    },
    "business.checkout": {
      "file": "docs/checkout.md",
      "section": "支付完成",
      "summary": "结账成功后的状态和副作用",
      "when": ["plan", "implement", "verify"]
    }
  }
}
```

示例字段路径和文件名只说明格式，省略了实际内容摘要；投放时必须按项目实际结构改写并建立摘要基线。索引最多 256 KiB、512 条；不以扩大索引代替明确选择读取范围。

- key 使用 1–128 个小写 ASCII 字母、数字、点、下划线或连字符，中文名称放在别名或摘要；不使用原型属性名。
- `file` 是项目根内的非秘密文件相对路径，不接受绝对路径、`..`、Git 元数据、秘密文件或符号链接跳转。
- 无 `section`、`select` 时读取整个文件。两者只能选其一。
- `section` 使用 Markdown 标题名或明确 anchor，读取该标题及下级标题的完整子树。重复标题名要用明确 anchor 消除歧义。
- `select` 是 YAML/JSON 中**一个字段路径**的段数组，例如 `["environment", "commands", "test"]`；每项都是一个字段名，不是多个点分查询，不执行表达式或查询语言。
- `aliases` 提供唯一的精确别名；`summary` 只参与定位，不保存取代来源正文的结论。
- `when` 只从 `start`、`plan`、`implement`、`verify`、`handoff` 选择，供节点读取选取候选；不记录流程完成状态。
- `sha256` 可保存被引用文件的摘要。更新工具能捕获当前正文文件摘要；它只能检测版本变化。
- 带综合结论条目的 `sources` 为 `[{"file":"源文件相对路径","sha256":"本次核实的SHA-256"}]`，适用于已有归属的说明和新增派生文档。Agent 明确读过当前源、修正或重证结论后才更新依赖摘要，不能只刷新 hash 消除提示。

## 检索与来源检查

命令中的 `{baseDir}`、`{target}` 与 key 都须替换，路径含空格时引用。使用技能入口确定的 `${BUN_X}`，下例不代表 CLI 执行项目命令。

```sh
${BUN_X} "{baseDir}/scripts/main.ts" context search "{target}" "支付 状态" --limit 8
${BUN_X} "{baseDir}/scripts/main.ts" context get "{target}" workflow business.checkout
${BUN_X} "{baseDir}/scripts/main.ts" context check "{target}" --changed docs/checkout.md --keys business.checkout
${BUN_X} "{baseDir}/scripts/main.ts" context node "{target}" plan --keys business.checkout --task tasks/checkout-fix.md --max-bytes 16384
```

| 命令 | 行为与使用时机 |
| --- | --- |
| `search TARGET QUERY [--limit N]` | 仅搜索 key、别名、摘要等索引元数据，不读取来源正文。用于尚不知道 key 时缩小范围。 |
| `get TARGET ID... [--max-bytes N]` | 精确 key 或别名批量读取。知道所需 key 时直接使用，避免先 search。 |
| `check TARGET [--changed FILE...] [--keys ID...]` | 只检查指定 key 和与变化文件关联的条目；不传过滤条件时才全索引检查。只读，不刷新摘要。 |
| `node TARGET NODE [--keys ID...] [--changed FILE...] [--task REL] [--max-bytes N]` | 按节点候选、明确 key、变化文件和显式任务组成一次读取；返回材料供 Agent 判断，不执行后续工作。 |

先看读取结果是否覆盖需求，再依靠原始内容作判断。来源不可读、重复标题歧义、缺 key、超预算和依赖过期都不能当成“没有此规则”。必要时缩小到更具体的段落或字段，分批读取并记录仍未覆盖的项。

合法查询未找到 key 或别名有歧义时返回 `failed`；超预算、搜索无命中或节点没有可用路由时返回 `unverified`，两者退出码均为 1。非法 schema、路径或参数退出码为 2。检查调用结果与未覆盖项，不能仅凭命令已执行判断读取成功。

`get/node` 每次最多返回 32 项正文，默认正文预算为 16 KiB，以字节计；超预算整项略过并报告 `omitted`、`uncovered` 或问题，不静默截断一条材料。来源读取还有单文件 512 KiB、合计 8 MiB 的上限，超限保留未覆盖项。`check` 可以核查本次选中的全部条目，返回的条目与问题列表最多 32 项，并附总数或省略数量；不能把返回列表长度当作实际检查数量。

结果的 `entries` 含 `id`、`file`、`status` 等信息；只有预算内且依赖未过期的项才含 `content`。显式 `--task` 的读取结果位于 `task`，也受正文预算限制。`index_sha256` 标识本次读取的索引版本，供后续更新计划使用。`metrics` 的 `index_bytes`、`source_bytes_read`、`returned_bytes`、`files_read`、`duration_ms` 描述本次操作，不是 token 消耗或端到端性能保证。

直接引用正文的文件变化时，结果标记 `changed` 并返回当前内容，让 Agent 核实后更新索引。条目任一 `sources` 摘要过期时标记 `stale`，不返回旧综合结论正文；Agent 改读已变化的源并重新判断结论。来源变化不自动证明结论错误，摘要相同也不证明结论正确。

## 增量更新

先修正内容所属文档或任务记录，再更新受影响索引项。新增 key 前搜索现有 key、别名和归属，避免另存同一事实。只改本次需要的条目，不重建整份索引，不触碰并行任务的条目。

```json
{
  "schema_version": 1,
  "expected_sha256": null,
  "upsert": {
    "workflow": {
      "file": "AGENTS.md",
      "section": "开发工作流",
      "summary": "任务各节点的读取、验证和维护责任",
      "when": ["start", "plan", "handoff"]
    }
  },
  "remove": []
}
```

```sh
${BUN_X} "{baseDir}/scripts/main.ts" context update "{target}" --plan "{target}/.agents/state/bootstrap/<run>/index-plan.json" --dry-run
${BUN_X} "{baseDir}/scripts/main.ts" context update "{target}" --plan "{target}/.agents/state/bootstrap/<run>/index-plan.json"
```

`expected_sha256` 在新建索引时为 `null`，修改时必须使用本轮读取结果的 `index_sha256`；不匹配则保留现场，重新合并。`upsert` 只新增或替换所列条目，`remove` 只移除所列 key，其他条目原样保留。`sources` 的摘要必须由 Agent 显式提供并与当前源匹配；工具只为条目自身 `file` 捕获摘要，不替 Agent 确认派生语义。

保存 `index-plan.json` 前审查拟写入字段和现有索引正文，并使用本轮私有运行目录，见 `references/recovery.md` 的“写入前”。更新沿用 `apply` 的敏感内容预检、比较摘要写入和收据机制。`--receipt` 可指定 `.agents/state/bootstrap/` 下的项目相对路径。它只写索引及本机收据。发生冲突时重新读当前内容和所需来源，保留他人工作后生成新计划。

普通 `apply` 发现已有索引时，写后只检查本轮变化文件关联的条目，在 `context_updates` 提示待复核项，成功的文件操作仍为 `passed`。`verify` 默认发现索引时合并索引检查；限定 `--paths` 时需显式包含 `.agents/context/index.json` 才纳入。它们不会刷新源摘要或重写结论，Agent 仍负责核实和维护。

## 合并到项目入口的协议

以下片段供 Agent 按项目实际路径、key 与工作流合并到目标 AGENTS。将“经验库”链接到接入时选定的项目位置。已有相同职责时直接合并，避免重复。

```markdown
## 上下文读取与维护

先读本项目开发工作流，再从 `.agents/context/index.json` 选择本次所需 key。已知 key 就批量精确读取；未知 key 先搜索索引元数据，再读相关段落或 YAML/JSON 字段。摘要只帮助定位，不作为业务事实。仅加载任务相关内容，保留未覆盖项。

用户明确调用 `kane-agent-bootstrap` 且工具可用时，从当前运行时可见的技能入口定位工具目录，按其 `context get/search/check/node/update` 使用；项目规则不写本机绝对技能路径。未明确调用本技能或工具不可用时，直接读取索引和条目指向的当前段落或字段，并照同一协议维护项目文件；本协议不自动触发技能，不暂停日常任务，不复制整套技能。

在开始、计划、实施、验证、交接节点主动取得相关上下文；来源或任务假设变化时重新读取并修正受影响结论。节点责任见本项目开发工作流。没有客户端 hooks 保证自动调用，执行任务的 Agent 对这些动作负责。

同一任务中已经读入且来源版本未变的内容可以复用。节点触发的是核对所需信息与新鲜度，不要求重复输出全文；用来源检查定位变化后，只补读新增、过期或尚未覆盖的条目。

真实环境在 `project.yml` 和实际配置，业务知识在已有所属文档，本次任务在当前请求明确的任务文件或 Issue；不建立全局 active_task 或重复的 raw 资料。按任务查阅经验库，交接时按本项目工作流写回有证据、可复用的新发现。先改事实所属来源，再增量维护受影响索引。只有确需新建的跨来源稳定结论才进入 `.agents/context/derived/`，并记录源依赖。

交接前核对变化文件关联条目和本次已用 key。派生来源过期时先读当前源、修正或重证结论，再更新摘要，不能只刷新 hash。重要决策记录简短理由、来源和反证条件；下一步与缺口写回本次唯一任务记录。索引纳入版本控制，`.agents/state/` 本机状态继续忽略。
```

## 合并到实际工作流的节点

把以下节点职责与独立评审规则合并进已有实际工作流，为“经验库”填入相对该工作流文档的实际链接。小项目可放进 AGENTS 的 `## 开发工作流`。沿用项目适用的评审触发条件、执行分工和记录位置。每个节点只读当前需要的条目。

```markdown
## 开发工作流

1. 开始（start）：读取本工作流、真实命令入口和当前明确任务记录，恢复目标、边界、验收与未决事项。没有明确持久任务时沿用当前请求，不自动选择其他任务。按需调用 context node 的 start 节点或精确读取相应 key。
2. 计划（plan）：按本次业务与改动范围读取必要知识，核对实现入口、约束与来源冲突；把重要决策的简短理由、依据和反证条件记入本次唯一任务记录。未知信息只限制受影响动作。
3. 实施（implement）：读取受影响模块和规则的 key；代码、文档、外部事实或原有假设变化时及时重读来源，修正计划与结论。稳定知识写回所属文档，避免在任务记录重复长期正文。
4. 验证（verify）：重取本任务完成标准及真实验证命令，核对输入、环境、实际结果和未覆盖项；把证据与缺口写回任务记录。结构或来源摘要通过不替代业务验证，CLI 不代为执行命令。
5. 交接（handoff）：整理结果、关键结论、下一步和未决事项，再检查任务证据中是否有可复用的新发现。
   - 有证据支持且后续可复用时，按项目格式写回经验库，记录触发条件、已核实的原因、纠正方法、适用范围和可回查的证据（如任务、Issue 或验证报告）。已有同类条目时合并，并补充证据或适用差异。待证实的观察留在任务记录。
   - 完成正文维护后仅更新受影响的索引项。用 context check 的 --changed 与 --keys 检查本次相关条目，重新核实 stale 项；无工具时做同等来源核对。以业务验收和真实证据判断完成，不用流程字段齐全证明完成。

### 独立评审与问题闭环

- 涉及权限、持久数据迁移、跨模块契约，或改变验收可信度的验证工具及门禁时，按项目风险在实施前评审方案，并在交付前独立评审最终差异与证据。计划评审者未参与计划编写，变更评审者未参与实施或修复。
- 明确以全新上下文发起独立评审，显式提供原始需求与验收、适用规范、待审计划或最终差异、相关实现和验证证据。评审者独立核实缺陷的位置、触发条件和影响。无法获得独立执行或隔离能力时，记录限制、自查覆盖和未解决风险。
- 逐项核实评审发现，记录处理结果及依据。修复后重跑受影响的检查，再由未参与该修复的审阅者复核相关发现及最终差异。保留未证实、未解决或未覆盖的问题和原因，在交接时报告其影响。
```

用户明确调用本技能且工具可用时，Agent 在节点主动调用 `context node TARGET NODE` 并显式补充所需 key、变化文件与任务路径；未调用时按项目协议直接读取来源。`when` 候选只是帮助选择；工具不知道用户真正目标和所有业务关联，不足的读取由 Agent 补充。

正文预算优先分给当前明确任务，再给显式 key、变化关联项和自动候选。未覆盖的变化文件需要 Agent 判断影响，不表示必须为每个文件建立索引项。

`node` 已完整读入的显式任务文件也算本次覆盖，出现在 `--changed` 时不要求重复建任务索引；若它是其他知识的依赖，相关条目仍会被检查。`update` 的 `writes_performed` 统计已确认的索引文件写入，dry-run 或无变化为 0，成功写入为 1，部分失败无法确认时为 `null`；不统计恢复收据等辅助写入。

## 边界与效果核对

`context` CLI 不做 LLM 语义判断、需求审批、项目命令执行或客户端调度。读取和更新协议随项目 AGENTS 加载后，由 Agent 按触发节点主动执行；这是遵循项目规则，不代表自动加载或调用本技能，也不表示已安装 hooks 或程序强制执行。

交付时核对三类结果：入口与实际工作流能否找到协议；本次所需来源是否正确且在预算内读全；来源变化后相关条目是否被发现、结论是否重新核实。可记录实际读取量、工具轮次、正确来源命中和过期项比例。无需新建通用硬验收清单或让人维护运行台账；不承诺最少轮次、最快检索或恒定端到端耗时。
