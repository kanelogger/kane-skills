# 深度模式：代码审查与必要检查

仅在深度模式读取，与入口同时加载的全面模式参考文档配合使用。选择深度即授权执行与本次改动相称的本地代码审查和现有检查；不因此授权推送、修改业务代码、变更生产数据或部署。

## 相关代码审查

从暂存 diff 出发，追踪理解该改动所必需的调用方、被调用实现、类型、配置和测试。重点检查逻辑及边界条件、错误处理、接口兼容性、敏感信息处理和回归风险；只在改动涉及相应机制时检查相关问题，不扫描整个仓库或泛化为完整安全审计。

用路径和可用时的行号说明实质问题及影响，区分已证实的问题和未验证的推测。对影响正确性、安全或兼容性的未解决问题，停在提交前。不要自动修复、重构或增补测试；把修复交还后续任务。

## 选择并执行检查

1. 根据仓库已有指令、脚本和改动范围，选择能够验证本次行为的现有测试、类型检查、lint 或构建。只执行必要的组合，不机械地全跑；纯文档改动使用相关文档、链接或格式检查。
2. 先确认检查的输入确实包含待提交候选。若工作区有会影响结果的无关改动或同文件未暂存 hunk，使用可用的隔离方式验证确切候选；不要 stash、还原或覆盖他人改动。无法可靠隔离时报告覆盖缺口并停在提交前，不把混合工作区的通过结果当作候选已通过。
3. 执行选定检查，记录命令、覆盖范围和实际结果。优先复用当前候选版本已经执行且范围足够的有效结果；变化使证据失效时重跑相关部分。不为检查安装新工具、引入新依赖或触发部署、付费服务及生产写操作。
4. 有相关检查失败、必需检查无法执行，或有实质审查问题未解决时，报告原因并停止提交，不自动重试或修复。已确认与本次无关的既有失败仍须如实记录；不能排除相关性时不能当作通过。

检查改变工作区或索引时重新确认候选和无关改动保护情况，不能顺带提交自动修复或生成文件。检查全部满足后，将审查结论和实际验证结果写入全面模式规定的提交记录，再回到入口提交。
