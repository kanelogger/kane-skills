# 全面模式：复核改动与提交记录

仅在全面或深度模式读取。全面模式不主动执行测试、构建、lint、类型检查或功能验收；深度模式的额外工作由 [deep.md](deep.md) 定义。

## 复核改动

以确切的暂存 diff 为边界，确认每处改动与任务目的相符，检查明显的逻辑错误、遗漏、接口或配置不一致、意外删除及破坏性变更。为理解改动可读取必要的相邻代码、测试和已有任务材料，不扩展为整个仓库的审计。

明确影响正确性或安全且尚未解决的问题，应说明路径、问题和影响，停在提交前，不自动修改源文件。一般建议可如实报告，不为补齐建议扩大任务。若复核期间索引变化，按入口要求重新复核候选。

## 生成提交信息

标题采用入口的 Conventional Commit 格式。空一行后，正文依次包含以下四部分，标签和内容使用选定的自然语言：

- **改动**：根据暂存 diff 概述具体变化及影响的行为或文件。
- **原因**：采用用户说明、已有任务材料或有依据的推断。不编造动机；依据不足时如实写“原因未提供，无法从现有材料可靠推断”，不为补齐正文追加访谈。
- **验证**：记录已有命令或操作、实际结果、执行环境和覆盖范围（已知时），以及未验证项。用户提供的结果注明来源；旧版本结果不等于本次通过。无执行记录写“未验证（无已有执行记录）”，建议标为“建议步骤（未执行）”。深度模式把本次实际检查及结果一并记录，失败或阻塞不得写成通过。
- **回滚**：纯代码或文档改动可写 `git revert <本次提交哈希>`，占位符由提交生成后取得的哈希替换在最终报告中，不为此 amend；不写成 `HEAD` 或提交前哈希。涉及数据、外部配置或部署时，注明额外恢复步骤、顺序、前置条件和不可逆限制，依据不足写“恢复步骤待补充”。只记录，不执行回滚，不承诺撤销代码即可恢复外部状态。

确有破坏性变更时，在正文后加 `BREAKING CHANGE: <说明>`。校验四部分齐全、与最终候选一致、证据状态真实、无敏感取值。缺少验证证据或恢复依据时明确记录缺口，不虚构或为补齐正文自行操作。
