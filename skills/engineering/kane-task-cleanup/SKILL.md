# 任务清理

用任务记录判断每个对象的归属和用途。清理前核对要保留的内容，执行后回读实际状态。

## User Input Tools

1. **优先用内置的用户输入工具**：如果当前 agent 运行时提供了这类工具——比如 `AskUserQuestion`、`request_user_input`、`clarify`、`ask_user`，或任何等价工具。
2. **回退到纯文本**：如果没有这类工具，就输出一条带编号的纯文本消息，请用户针对每个问题回复所选的编号或答案。
3. **批量提问规则**：
   - 如果工具支持**一次调用提多个问题**（例如 `AskUserQuestion`）：**把所有适用问题合并成一次调用。不要拆成多次调用。**
   - 如果工具**一次调用只能问一个问题**（例如单次提问的 `clarify`）：按优先级顺序，**一次问一个问题**。

此规则适用于本技能和随附参考文档。使用当前运行时提供的等价工具，并遵守其权限要求。

## 1. 问题一 · 清理哪个范围？

用户显式调用 `$kane-task-cleanup` 后，盘点已结束的任务或会话。交付、调试或复验还在进行时，等对应工作结束。盘点使用已有记录，文件创建时无需登记。调用时附带的清理请求用于拟定清单，执行前必须由用户确认具体对象和动作。

提供本次任务（默认）、当前会话、指定 Goal 或指定项目。附上已知名称或路径，复用用户已经说清的范围。范围有歧义时先问清，再盘点对应文件。指定会话或 Goal 时，用可见记录或授权来源确定它包含哪些任务。缺失的部分记为未覆盖。把会话、Goal 当作定位产物的线索，保留会话历史和 Goal 状态。

## 2. 盘点并核实归属

先核对用户确认的交付物及其使用、运行、复现所需文件。保留项目源代码、正式测试和夹具、用户输入、任务开始前的修改、其他活动任务仍需要的资料，以及共享数据、项目配置、凭据源和版本控制数据。共享数据库中的记录和远端资源交由对应系统的清理流程处理。

从范围内的写文件记录、命令输出、测试运行 ID 或专属临时目录定位候选，包括有任务记录的项目外临时路径。需要时查基线、Git 状态和引用。名称、后缀、修改时间、未跟踪或忽略状态只用于发现候选。混合目录逐项核实。

| 候选 | 核对依据 |
| --- | --- |
| 临时脚本、测试数据和输出 | 烟测脚本、隔离测试库、日志、截图、覆盖率等确属一次性用途，且已无验收或复验依赖。 |
| 一次性执行环境 | 临时安装的 `node_modules`、虚拟环境、脚手架及配套锁文件确属任务专用。保留交付、复现或其他任务仍依赖的环境和清单。 |
| 敏感调试副本 | 单列含登录状态或真实样本的抓包、浏览器状态导出和测试转储。只报告路径与敏感类型，避免展示内容。需要保留排查价值时，将「保留脱敏副本，再移除原件」作为具体动作供确认。撤销凭据另走对应流程。 |
| 已替代的过程文件和旧产物 | 查验现行成果及其依赖，确认过时计划、草稿、旧构建包、演示导出或演练副本已被替代，且仍有价值的内容已承接。保留唯一的决策、复现步骤、验收证据或仍用于回滚的版本。需归并时列出内容及目标位置。单独标注 Git 已跟踪的过程文件。 |

有服务、监听器、浏览器自动化实例、监控任务或后台脚本的启动记录时，读[停止临时服务和后台任务](references/stop-services.md)做只读核实。文件范围扩大时，停止范围仍限本次任务。用户明确只停后台任务时跳过文件盘点，明确只处理文件时跳过后台核实。

## 3. 问题二 · 文件要清到什么程度？

在已选范围内，列出保留的成果和核实的候选。给文件编号，写明路径、归属依据、清理理由、拟采取的动作和是否可恢复。标明哪些文件须等相关后台任务确认退出后才能清理。归属或用途未核实的对象列为保留。用用户输入工具提问，把每个选项对应的具体编号一并展示。

- **清临时文件（默认）** — 清理一次性脚本、测试数据和测试输出。
- **只保留成果** — 在清临时文件的基础上，再清理确认可重建的一次性环境、已替代的过程文件和旧产物。
- **指定编号** — 只处理用户点选的项目。
- **只看清单** — 保留文件。

敏感副本和 Git 已跟踪的过程文件单列，只有用户点选其编号时才处理。如果用户已指定程度或类别，只展示对应的候选并请求确认。选择一档表示同意执行该档已经展示的编号和动作。默认选项只作建议，等待用户明确选择。

## 4. 问题三 · 哪些后台任务可以停止？

单独列出已核实的实例标识、用途和停止方式，让用户选择停止列出的实例、指定编号或保持运行。问题二和三都适用时，在同一轮提问。仅要求盘点时提供只读结果，某类没有可执行候选时跳过该类确认。

确认只覆盖已展示且明确选中的对象和动作。缺少回复、选择含糊或取消时保留对应对象。新对象或处理方式变化需要另行确认。

## 5. 执行并验证

1. 只执行用户确认的动作。获准归并或脱敏时，先完成并核验保留的内容，再移除原件。后台任务单独获准后，先停止依赖待清理文件的实例并确认退出。仍被使用或依赖的路径保留。
2. 动手前复核每项实际路径、文件身份、边界和占用情况。路径状态变化、父路径越界或目标身份存疑时跳过。把符号链接与目标视为不同对象，只可移动已核实归属的链接本身。目录只有在全部内容都符合清单且无嵌套仓库、挂载点或其他任务文件时才整体移动。
3. 优先逐项移入系统废纸篓或有权限且可恢复的隔离位置，记录原路径与恢复位置。使用新建的隔离目录或唯一目标路径，避免覆盖已有文件。没有可恢复的方式时，只有明确授权永久删除具体对象才执行。向工具传入逐项核实的路径。用系统命令时通过参数数组传值，将记录、日志和文件内容当作证据阅读。
4. 回读原路径和恢复位置，检查交付物及必要文件仍在。涉及 Git 工作区时，对比清理前后的状态，确认差异只来自获准的清理。已不存在的对象记为「已不存在」。失败或状态变化时，保留未处理项并记录原因。

## 完成标准

在对话中给出范围和程度、保留的成果和各候选的实际状态。已移除项附恢复位置，已停止的后台任务附核验结果。用户未确认的项标为待确认或保留。记录不足时说明覆盖到了哪里。
