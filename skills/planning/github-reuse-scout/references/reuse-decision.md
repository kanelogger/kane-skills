# 复用决策 Rubric

阶段 4 按本文件逐维评估候选仓库，得出 `fork` / `reference` / `none` 之一，并写入 `.reuse/reuse-plan.md`。

## 硬性排除（命中任一条直接出局，无需深入检查）

- 仓库已 archived；
- 无 license（无法判断许可）；
- pushed_at 超过 18 个月 且 stars < 50（基本停更且无社区）；
- 领域完全不匹配（核心对象/流程与需求无关）。

## 四个评估维度

1. **领域匹配**：需求的核心对象与流程在项目中的覆盖率。
   - 高：≥70% 的核心对象/流程可见（README、目录、数据模型）；
   - 中：主要流程覆盖但对象有出入；
   - 低：只有局部功能重叠。
2. **架构契合**：模块边界与需求域的吻合程度。
   - 高：模块边界清晰、可裁剪（独立目录/包、接口明确）；
   - 中：能裁剪但要动不少胶水代码；
   - 低：单体高度耦合，难以取用部分。
3. **可维护性**：license 许可（Apache-2.0/MIT/BSD/ISC/Mozilla → 允许；GPL/AGPL → 默认不直接复用，需问用户）、活动度（pushed ≤ 18 个月）、社区（stars/forks）。
4. **技术栈偏差**：与目标框架的距离。同语言同生态 → 低；同语言异框架 → 中；异语言 → 高。

## 决策规则

- `fork`（基于现有项目开发）= 领域匹配**高** AND 架构契合**高** AND license 允许 AND 栈偏差**低-中**。
- `reference`（参考架构自建，不抄代码）= 领域匹配**中-高** AND 架构契合**高**，但命中以下任一：
  license 不允许（含用户拒绝 GPL）、栈偏差**高**、上游代码质量低（无测试/无文档/结构混乱）。
- `none`（不复用）= 其余情况。必须记录"缺什么就能复用"（如：需要 X 领域且活跃的 MIT 项目）。

## A/B 规则

- A 类（自动判定，不打扰用户）：领域匹配度、架构契合度、活动度、license 类型、代码质量。
- B 类（必须问用户，决策时一次问清）：
  - 目标框架（迁移目的地）；
  - GPL/AGPL 是否可接受；
  - 自托管/部署约束；
  - 是否接受大型单体。
- 目标框架未答 → `reuse-plan.md` 中目标框架记 `待确认`，迁移挂起，不阻塞 fork 启动开发。

## 决策前证据要求

- 必须已读排名第 1 候选的 evidence（README 头、清单、目录树）。
- 评分与证据来自脚本产物（`.reuse/scored.json`、`.reuse/evidence/`）；脚本不可用时改用手动查询，
  并在 `reuse-plan.md` 决策依据中注明证据来源为手动。
