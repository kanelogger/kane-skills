# kane-explainer

把技术规格、RFC、设计提案或当前工作区中的变更，解释成一份不依赖原始上下文也能读懂的中文说明。

核心原则：**降低理解门槛，不降低事实精度。** 读者可以不了解代码、diff 和讨论历史，但应能看懂具体场景、控制流程、数据流与契约变化。

## 适用场景

- 解释一项技术变更解决了什么问题，以及现有行为为何会产生该问题。
- 用“变更前 → 变更后”的方式讲清方案如何运作。
- 向没有参与开发的技术读者介绍 RFC、规格说明或拟议方案。
- 盘点 schema、持久化格式、线上传输格式、游标或读取方契约的变化。
- 区分已经存在的行为、当前实现的行为与尚未落地的提议。

它不是逐行 diff 解读器，也不会用宽泛类比替代真实的行为和边界。

## 如何使用

最好明确提供需要解释的成果物，例如规格说明、RFC、设计文档或变更范围：

```text
请使用 kane-explainer 解释 docs/rfc/event-cursor.md，
重点说明重复调用时的行为，以及游标格式是否需要迁移。
```

也可以直接解释当前会话正在处理的变更：

```text
请使用 kane-explainer 解释当前工作区的改动，
让没有看过 diff 的技术读者也能独立理解。
```

如果规格说明不足以确定真实行为，技能会继续查看相关代码；如果没有指定成果物，则以当前会话中的工作区或分支变更为解释对象。

## 工作方式

1. **建立边界**：确认解释对象，并区分现状、已实现变更和仅被提议的方案。
2. **还原问题**：从用户操作或系统后果出发，完整走一遍“触发事件 → 当前行为 → 问题结果”。
3. **解释方案**：用职责而不是文件名介绍组件，给出清晰的“变更前 → 变更后”数据流。
4. **展开决策**：遇到条件、顺序、时机或重复调用时，用决策层伪代码明确各条路径。
5. **盘点契约**：穷尽 schema 和持久契约的新增、修改、删除、重置与刻意保持不变的部分。

解释中会特别区分权威记录与派生索引、缓存、摘要、展示分组等从属产物，并直接指出迁移、兼容性、最终一致性、破坏性重置和有意数据丢失等影响。

## 固定输出

输出严格按以下顺序组织：

```markdown
## Problem

问题发生的具体场景、当前行为及其后果。

## Solution

变更后的数据流、决策顺序、组件职责与关键边界。

## Schema changes

所有持久契约变化；如果没有变化，明确写出“无 schema 变更”。

一句话说明用户在此次变更后应当注意到的变化。
```

### Schema 盘点范围

- 新增、修改或删除的字段、记录、索引和格式。
- 需要重置、回填或迁移的数据。
- 游标和线上传输格式对已有存储数据及读取方的影响。
- 兼容旧版本的行为，以及明确不再兼容的边界。
- 刻意保持不变、但容易被误以为发生变化的契约。

## 表达要求

- 专业术语第一次出现时立即定义。
- 用短小、具体、可从头走到尾的例子承载精确描述。
- 出现“只有当”“在此之前”“除非”“一旦……就”等条件关系时，优先使用伪代码。
- 说明第二次调用会发生什么，避免用抽象描述掩盖时序问题。
- 最终文本必须脱离代码、diff、规格说明和对话记录后仍可独立成立。

## 补充场景：图解 HTML

当主题抽象、读者缺少背景，或需要更直观的演示材料时，可以追加以下要求：

> 请把我当成对这个话题一无所知的人，用一个包含大图且文字较少的 HTML 组件来向我解释。

图解可以改变呈现形式，但不能省略 `Problem`、`Solution`、`Schema changes` 三部分的事实，也不能用类比代替真实的控制流程、数据流或兼容性边界。适合把完整场景画成一张主流程图，用短标签标出触发点、状态变化和最终结果。

## 完成标准

没有读过原始材料的技术读者，应能仅凭输出回答：

1. 什么事件触发了问题？
2. 当前系统会怎样处理，为什么会出错或产生限制？
3. 变更后按什么顺序处理，同一操作再次发生时会怎样？
4. 哪些数据契约发生了变化，是否需要迁移、重置或兼容旧数据？
5. 用户最终会观察到什么不同？
